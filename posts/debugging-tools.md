**不会调试就等于不会开发。** 这句话在嵌入式领域尤其成立——因为你无法在真实硬件上随意打断点、加日志、改代码重启，硬件的行为必须靠仪器去"看"。

这篇文章讲清楚三类核心工具各解决什么问题，以及怎么用它们定位真实故障。

## 一、工具全景

| 工具 | 解决什么 | 预算 | 优先级 |
|---|---|---|---|
| USB 转串口 | 打印日志 | 10-30 元 | ★★★★★ |
| 调试器（ST-Link/J-Link） | 单步、断点、看变量 | 20-300 元 | ★★★★★ |
| 万用表 | 电压、通断、电流 | 50-200 元 | ★★★★★ |
| 逻辑分析仪 | 数字时序（I2C/SPI/UART） | 30-100 元 | ★★★★☆ |
| 示波器 | 模拟信号、电源质量 | 500-3000 元 | ★★★☆☆ |
| 热成像仪 | 发热定位 | 500+ 元 | ★★☆☆☆ |

**新手起步建议**：串口 + ST-Link + 万用表 + 逻辑分析仪，**总价 200 元以内**，能覆盖 90% 的调试场景。

## 二、串口：最便宜的调试手段

串口打印是**性价比最高的调试方式**。一个 10 块钱的 USB 转 TTL 模块，能让你看到程序内部的运行状态。

### 2.1 硬件接线

```
USB 转串口模块         目标板
   TX  ──────────────►  RX
   RX  ◄──────────────  TX
   GND ───────────────  GND     ← 必须接！
   3V3 ───────────────  (可选，不要和板子自己的供电冲突)
```

**TX 接 RX、RX 接 TX 是必须交叉的**，接反了没有任何输出。另外 **GND 一定要接**，只接两根信号线的话电平没有参考，收到的全是乱码。

### 2.2 电平匹配

| 模块 | 电平 | 注意 |
|---|---|---|
| USB-TTL（CH340/CP2102） | 3.3V 或 5V | 多数有跳线可选，**选 3.3V** |
| RS232 转 USB | ±12V | **绝对不能直接接 MCU**，会烧引脚 |

用 RS232 电平和 3.3V MCU 直连是新手最容易犯的致命错误。买模块时看清楚是"USB 转 TTL"还是"USB 转 RS232"。

### 2.3 让日志真正有用

裸 `printf` 撑不了多久，日志量一大就淹没在输出里。几个改进：

**分级 + 时间戳 + 文件行号：**

```c
#include <stdio.h>

#define LOG_LEVEL_NONE  0
#define LOG_LEVEL_ERROR 1
#define LOG_LEVEL_WARN  2
#define LOG_LEVEL_INFO  3
#define LOG_LEVEL_DEBUG 4

#ifndef LOG_LEVEL
#define LOG_LEVEL LOG_LEVEL_INFO
#endif

#define LOG_PRINT(lv, tag, fmt, ...)                                    \
    do {                                                                \
        if ((lv) <= LOG_LEVEL) {                                        \
            printf("[%8lu][%s] " fmt "\r\n",                            \
                   (unsigned long)HAL_GetTick(), tag, ##__VA_ARGS__);   \
        }                                                               \
    } while (0)

#define LOGE(tag, fmt, ...) LOG_PRINT(LOG_LEVEL_ERROR, tag, fmt, ##__VA_ARGS__)
#define LOGW(tag, fmt, ...) LOG_PRINT(LOG_LEVEL_WARN,  tag, fmt, ##__VA_ARGS__)
#define LOGI(tag, fmt, ...) LOG_PRINT(LOG_LEVEL_INFO,  tag, fmt, ##__VA_ARGS__)
#define LOGD(tag, fmt, ...) LOG_PRINT(LOG_LEVEL_DEBUG, tag, fmt, ##__VA_ARGS__)
```

输出效果：

```
[    1234][WIFI] 连接失败, retry=3
[    5678][MQTT] 已连接 broker.emqx.io
[   12345][SENS] 温度 24.5 湿度 61.2
```

**时间戳是最有价值的部分**。它能一眼看出"两次操作之间隔了多久"——很多问题（任务阻塞、看门狗超时）本质上都是时间问题。

**生产版本要能整体关掉。** 把 `LOG_LEVEL` 设成 `LOG_LEVEL_ERROR`，所有 INFO/DEBUG 日志在编译期就被消除，不占任何代码空间和运行时间。

**不要在中断里打印。** 串口打印耗时可能几百微秒到几毫秒，在 ISR 里打印会严重破坏实时性，还可能与主循环的打印互相交错产生乱码。正确做法是在 ISR 里置标志，主循环里打印。

### 2.4 常见问题

| 现象 | 原因 |
|---|---|
| 全是乱码 | 波特率不匹配 / 晶振频率和代码里写的不一致 |
| 偶尔乱码 | 波特率误差偏大（用了内部 RC）/ 电源不稳 |
| 完全没有输出 | TX/RX 接反 / GND 没接 / 引脚没配对 |
| 输出一段就卡住 | 发送缓冲区满，接收端没在读（流控问题） |
| 中文乱码 | 终端编码不是 UTF-8，或串口工具没设对 |

**波特率不匹配是乱码的头号原因**。特别注意：如果代码里按 72MHz 算的波特率，实际芯片跑的是 8MHz 内部时钟，那实际波特率会差 9 倍。

## 三、调试器：比打印更强大的武器

串口打印只能看到你主动输出的信息，**调试器能让你看到所有内存**。

### 3.1 常用功能

| 功能 | 用途 |
|---|---|
| 断点 | 停在指定位置，看当时状态 |
| **条件断点** | 只在条件满足时停下（变量等于某值、第 N 次命中） |
| 数据观察点 | **变量被修改时自动停下**——查"变量莫名其妙被改"的利器 |
| 单步 / 步过 | 逐行跟踪执行流 |
| 调用栈 | 看"我是怎么走到这里的" |
| 实时变量监视 | 不暂停运行也能周期刷新变量值 |

**数据观察点（Watchpoint）是排查内存踩踏的神器**。当某个变量在莫名其妙的地方被改成错误值时，设一个写观察点，调试器会在**写入发生的那一刻**停下，直接告诉你凶手是谁。

**实时变量监视（Live Watch）** 让你能像看示波器一样看变量变化，不打断程序运行。适合观察状态机流转、计数器变化。

### 3.2 HardFault 怎么定位

Cortex-M 遇到非法访问、除零、未对齐访问会进入 HardFault。默认的 `HardFault_Handler` 是个死循环，看不出任何信息。

**用一个能打印现场的实现替掉它：**

```c
/* 在启动文件里找到 HardFault_Handler 的定义，用 weak 覆盖它 */
void HardFault_Handler(void)
{
    __asm volatile (
        "tst lr, #4          \n"   /* 检查 EXC_RETURN 的 bit2 */
        "ite eq              \n"
        "mrseq r0, msp       \n"   /* 从主栈取 */
        "mrsne r0, psp       \n"   /* 或从进程栈取 */
        "mov r1, lr          \n"
        "b hard_fault_report \n"
    );
}

/* 参数是压栈的寄存器组 */
void hard_fault_report(uint32_t *stack, uint32_t lr)
{
    printf("\r\n===== HardFault =====\r\n");
    printf("R0  = 0x%08lX\r\n", (unsigned long)stack[0]);
    printf("R1  = 0x%08lX\r\n", (unsigned long)stack[1]);
    printf("R2  = 0x%08lX\r\n", (unsigned long)stack[2]);
    printf("R3  = 0x%08lX\r\n", (unsigned long)stack[3]);
    printf("R12 = 0x%08lX\r\n", (unsigned long)stack[4]);
    printf("LR  = 0x%08lX\r\n", (unsigned long)stack[5]);
    printf("PC  = 0x%08lX  ← 出错位置\r\n", (unsigned long)stack[6]);
    printf("xPSR= 0x%08lX\r\n", (unsigned long)stack[7]);

    for (;;);
}
```

**`PC` 就是出错的指令地址**。在 Keil 里用 `Disassembly` 窗口跳转到这个地址，或者用 `fromelf --text -c firmware.axf` 反汇编后查找，就能定位到具体哪一行代码。

如果开了 `__disable_irq()`，HardFault 处理函数里 printf 可能发不出去。稳妥做法是把这些值存到全局变量里，重启后查看，或者用调试器看。

### 3.3 用调试器看栈溢出

RTOS 项目里栈溢出很隐蔽。除了 FreeRTOS 自带的高水位线功能，还可以**在栈的头部填一个魔数**，定期检查是否被改写：

```c
#define STACK_MAGIC 0xDEADBEEF

/* 任务启动时填充魔数 */
void vTaskWithGuard(void *p)
{
    uint32_t guard[16];
    for (int i = 0; i < 16; i++) guard[i] = STACK_MAGIC;

    /* ... 任务主体 ... */

    /* 检查魔数是否完好 */
    for (int i = 0; i < 16; i++) {
        if (guard[i] != STACK_MAGIC) {
            printf("栈越界！位置 %d\r\n", i);
        }
    }
}
```

## 四、逻辑分析仪：看清数字时序

串口和调试器都看不到**引脚上实际发生了什么**。逻辑分析仪补上这一环。

它和示波器的区别：

| | 逻辑分析仪 | 示波器 |
|---|---|---|
| 看什么 | 高低电平（0/1） | 电压的连续变化 |
| 通道数 | 8/16 通道常见 | 2/4 通道 |
| 采样率 | 高，但只看阈值 | 看波形细节 |
| 协议解码 | **内置 I2C/SPI/UART 解码** | 少数支持 |
| 价格 | 几十元 | 几百元起 |

### 4.1 选型

- **入门**：8 通道 24MHz 的 USB 逻辑分析仪，30 元左右，配 PulseView（开源软件）完全够用
- **注意采样率**：至少要**信号频率的 5 倍**。I2C 400kHz 需要 2MHz 以上，SPI 20MHz 就需要 100MHz 采样——几十块的分析仪跟不上，得换更贵的
- **别买太便宜的 8 通道 24MHz 去看 SPI 高速信号**，采不到

### 4.2 实战：抓 I2C 波形

以读一个 SHT30 传感器为例：

**接线**：GND、SCL、SDA 三根，接到分析仪的 CH0/CH1。

**设置**：协议选 I2C，SCL 选 CH0，SDA 选 CH1，触发方式选"SCL 下降沿"。

**抓到的解码结果**：

```
START
  Write  0x44  ACK          ← 从机地址 0x44，写方向
  Data   0x2C  ACK          ← 命令高字节：周期测量
  Data   0x06  ACK          ← 命令低字节
STOP
...
START
  Read   0x45  ACK          ← 从机地址 0x45，读方向
  Data   0x61  ACK          ← 温度高字节
  Data   0x8F  NACK         ← 温度低字节
  Data   0x5C  ACK          ← CRC
  Data   0x2E  NACK
STOP
```

对照手册检查每一段，异常一眼可见：

| 观察 | 结论 |
|---|---|
| 地址后是 NACK | 从机地址错 / 器件没供电 |
| 有地址但无数据 | 命令字节错 / 器件需要转换延时 |
| 数据全 1 | 从机没驱动总线，检查上拉和供电 |
| 时钟频率不对 | 分频配置错 |
| 缺 STOP 条件 | 通信被中断打断 |

**这套方法对 SPI 同样适用**，而且 SPI 因为有时钟线，解码更简单。

### 4.3 实战：抓 UART 通信

接 TX 和 GND 即可。分析仪直接解码出 ASCII：

```
[  12.345] UART: 'A' 0x41
[  12.351] UART: 'T' 0x54
[  12.357] UART: '+' 0x2B
...
```

**验证内容对不对，同时也能看波特率是否准确**——分析仪测出的实际位宽和理论值对比，就能算出误差。

一个常见坑：收到的数据"每隔几个字节错一个"，通常是波特率误差接近临界值，或者发送端用了内部 RC 振荡器。

## 五、示波器：模拟世界的眼睛

逻辑分析仪只看 0 和 1，**看不出信号质量**。一个 3.3V 的信号可能是干净的方波，也可能是振铃严重的过冲波形——在逻辑分析仪眼里两者一模一样，但后者会导致偶发错误。

### 5.1 什么时候需要示波器

- **电源质量**：纹波、跌落、上电时序
- **高速信号完整性**：SPI 时钟波形、振铃、过冲
- **排查"随机死机"**：抓电源跌落瞬间
- **模拟信号**：PWM 占空比、ADC 输入、传感器输出

### 5.2 常见测量

**测电源纹波：**

```
探头设置：AC 耦合，带宽限制 20MHz
时基：1ms/div
电压：10mV/div
```

正常 3.3V 电源的纹波应该在 **50mV 以内**。超过 100mV 就可能引起 MCU 逻辑错误。

纹波大的原因通常是：
- 去耦电容漏了或离引脚太远
- LDO 输出电容选型不当（某些 LDO 需要特定 ESR 范围才能稳定）
- 地平面不完整

**测 SPI 时钟波形：**

```
探头设置：DC 耦合，全带宽
时基：10ns/div（看 20MHz 时钟）
```

健康的方波应该是平顶、边沿陡峭，过冲在 10% 以内。出现明显振铃说明：
- 走线太长或阻抗不匹配
- 需要串源端匹配电阻（22-33Ω）

**测上电时序：**

用两个通道同时看 VDD 和复位引脚：

```
CH1: VDD (3.3V/div)
CH2: nRST (3.3V/div)
触发: CH1 上升沿
```

正常顺序是 VDD 稳定后复位才释放。如果复位释放太早（VDD 还没稳），MCU 会在低压下启动失败——**这种板子表现为"偶尔上电不启动，断电重来就好"**。

解决办法是在复位电路上加 RC 延时：

```c
/* 硬件方案：复位引脚接 10k 上拉到 VDD + 100nF 到地
 * RC 时间常数 1ms，确保 VDD 稳定后才释放复位 */
```

### 5.3 使用注意

- **探头要校准**。用探头自带的方波输出校准补偿电容，否则测出来的波形是失真的
- **10:1 探头会引入负载电容（约 10pF）**，测晶振时可能让本来起振的电路停振
- **接地线要短**。长的接地线会形成天线引入噪声，测小信号时务必用弹簧地针
- **别用示波器测市电**，除非用隔离变压器或差分探头，否则会短路爆炸

## 六、几个真实案例

### 案例一：偶发死机，换了三块板子还是一样

**现象**：设备运行几小时后随机死机，重启正常。

**排查过程**：

1. 串口日志最后一条是正常的心跳，没有异常打印 → 不是软件逻辑问题
2. 加看门狗，发现确实触发了复位 → 说明程序真的跑飞了
3. 用调试器的数据观察点监视关键变量，没发现异常改写
4. 用示波器长时间监测 3.3V 电源，抓到死机瞬间有一次 **300mV 的跌落**

**根因**：继电器吸合时瞬时电流大，共用电源上产生了跌落，MCU 供电跌破 2.7V 导致复位。

**解决**：继电器和 MCU 电源分开，各自加 100μF 储能电容，MCU 侧加 100nF 去耦。

**教训**：**"随机死机"通常是电源问题**，优先用示波器查电源。

### 案例二：I2C 在面包板上正常，焊到板子上就不通

**现象**：同一套代码，面包板能用，做的板子不行。

**排查过程**：

1. 逻辑分析仪抓波形，发现 SCL 上升沿非常缓
2. 对比面包板和 PCB 的差异——PCB 走线更长
3. 万用表测上拉电阻，确认用的是内部上拉（40kΩ）

**根因**：内部 40kΩ 上拉配长走线的分布电容，RC 时间常数太大，上升沿超过了 I2C 的建立时间要求。

**解决**：加上 4.7kΩ 外部上拉，波形立刻变陡，通信正常。

**教训**：**I2C 一定要用外部上拉**，内部上拉只适合短线。

### 案例三：SPI 屏幕低速正常，一提速就花屏

**现象**：SPI 时钟 10MHz 时正常，调到 30MHz 就出现花屏。

**排查过程**：

1. 用示波器看 SCK 波形，发现明显振铃，过冲达到 1V
2. 检查 PCB，SCK 走线有 8cm 长，且是直连没有端接

**根因**：走线太长，阻抗不匹配导致信号反射。

**解决**：SCK 串 33Ω 源端匹配电阻，振铃基本消失，30MHz 稳定工作。

**教训**：**SPI 超过 20MHz 就要考虑信号完整性**，源端串阻是最简单的解决办法。

## 小结

| 工具 | 核心价值 | 什么时候用 |
|---|---|---|
| 串口 | 看程序内部状态 | 从第一天起就用 |
| 调试器 | 看所有内存、定位 HardFault | 打印解决不了的时候 |
| 逻辑分析仪 | 看数字时序 | 通信不通的时候 |
| 示波器 | 看信号质量 | 随机故障、电源问题 |
| 万用表 | 通断、电压、电流 | 硬件第一步排查 |

**调试能力的分水岭在于：遇到问题时，你是靠猜还是靠测。** 有工具的人会直接去看现象，没工具的人只能改代码试。

配齐前四样工具花不到 500 块，但它们能让你的开发效率提升好几倍。
