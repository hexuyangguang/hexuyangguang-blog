UART、I2C、SPI 是板级通信的三大件。传感器、存储器、显示屏、模组，几乎都走这三种接口之一。

这篇文章先横向对比它们的差异，再给出各自的驱动要点，最后讲怎么用逻辑分析仪快速排错。

## 一、横向对比

| 特性 | UART | I2C | SPI |
|---|---|---|---|
| 信号线 | 2（TX/RX） | 2（SCL/SDA） | 4（SCK/MOSI/MISO/CS） |
| 拓扑 | 点对点 | 多主多从，总线 | 一主多从，片选 |
| 时钟 | 异步（无时钟线） | 同步 | 同步 |
| 速率 | 通常 115200~1Mbps | 100k/400k/1M/3.4M | 常见 1~50MHz |
| 寻址 | 无 | 7 位地址（或 10 位） | 片选引脚 |
| 双工 | 全双工 | 半双工 | 全双工 |
| 上拉电阻 | 不需要 | **必须** | 不需要 |
| 引脚开销 | 2 / 每设备 | 2 / 所有设备 | 1 片选 / 每设备 |
| 典型器件 | 模组、PC 串口 | 传感器、EEPROM | Flash、屏幕、高速 ADC |

### 怎么选

- **设备在板外、距离远、只需单向通信** → UART。走线长、抗干扰相对好，还能加 RS485 转差分延长到上千米。
- **设备多、速率要求不高、想省引脚** → I2C。两根线挂十几个器件，代价是速率上不去。
- **要高速、要全双工** → SPI。屏幕刷图、Flash 读写基本都用它。

一个常见组合：MCU 用 SPI 驱动 LCD，用 I2C 读几个传感器，用 UART 连 4G 模组。**三种同时用完全没问题**，它们占用的引脚不冲突。

## 二、UART：看似简单，坑在细节

### 2.1 波特率必须精确匹配

UART 是异步的，双方没有共享时钟，靠约定的波特率采样。**收发双方误差通常不能超过 ±2%~3%**，否则会采样错位。

误差的来源是分频系数只能取整数：

```c
/* 波特率计算公式 */
// BRR = fCK / (16 × baud)          —— OVER8 = 0（16 倍过采样）
// BRR = fCK / (8  × baud)          —— OVER8 = 1（8 倍过采样）

/* 例：PCLK2 = 72MHz，想要 115200 */
// BRR = 72000000 / (16 × 115200) = 39.0625
// 只能取 39（或用小数波特率寄存器凑 39.0625）
```

72MHz 下 115200 的误差很小，但**如果用了内部 RC 振荡器（HSI）**，其本身就有 ±1% 的偏差，加上分频误差就可能超标。现象是"大部分数据对，偶尔错几个字节"。

**结论**：用串口通信一定要用外部晶振。

### 2.2 三个必须掌握的中断技巧

**接收不定长数据：用空闲中断。**

传感器的响应长度不固定，不知道要收多少字节。传统做法是"收一个字节进一次中断，超时判断结束"，效率低。用 IDLE 中断更优雅：

```c
/* 初始化：开启接收中断 + 空闲中断 */
HAL_UART_Receive_IT(&huart1, &rx_byte, 1);
__HAL_UART_ENABLE_IT(&huart1, UART_IT_IDLE);

/* 空闲中断回调：总线空闲超过一个字节时间说明一帧结束 */
void USART1_IRQHandler(void)
{
    if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_IDLE)) {
        __HAL_UART_CLEAR_IDLEFLAG(&huart1);     /* 必须先清标志 */
        /* 此时接收缓冲区里就是一整帧数据 */
        frame_complete(rx_buf, rx_len);
        rx_len = 0;
    }
    HAL_UART_IRQHandler(&huart1);
}
```

**清 IDLE 标志的方式很坑**：它不是普通的写 1 清零，而是"读 SR 再读 DR"。HAL 的 `__HAL_UART_CLEAR_IDLEFLAG` 宏已经封装好了，但**必须先于 `HAL_UART_IRQHandler` 调用**，否则会被后者清掉导致丢帧。

**发送别用阻塞式：**

```c
/* 阻塞式：发 100 字节 @115200 要 8.7ms，CPU 全耗在等 */
HAL_UART_Transmit(&huart1, buf, 100, HAL_MAX_DELAY);

/* DMA 方式：CPU 立刻返回，传输由 DMA 完成 */
HAL_UART_Transmit_DMA(&huart1, buf, 100);
```

日志打印量大时，阻塞发送会严重影响实时性。用 DMA + 环形缓冲区，能把 CPU 占用降到几乎为零。

**用重定向 printf 做日志，但要分级：**

```c
#define LOG_LEVEL 2       /* 0=none 1=error 2=info 3=debug */

#if LOG_LEVEL >= 1
  #define LOGE(fmt, ...) printf("[E] " fmt "\r\n", ##__VA_ARGS__)
#else
  #define LOGE(fmt, ...) ((void)0)
#endif

#if LOG_LEVEL >= 2
  #define LOGI(fmt, ...) printf("[I] " fmt "\r\n", ##__VA_ARGS__)
#else
  #define LOGI(fmt, ...) ((void)0)
#endif
```

发布版本把 `LOG_LEVEL` 调到 1，调试日志自动消失，**不产生任何运行时开销**（编译期就没了）。

## 三、I2C：时序严格，上拉是关键

### 3.1 硬件上最容易犯的错

**必须外接上拉电阻。** I2C 的 SCL 和 SDA 都是开漏输出，只能拉低不能拉高，高电平完全靠上拉电阻。内部 40kΩ 弱上拉在长导线上会导致上升沿过慢，波形变成这样：

```
理想:  ┌──────┐      ┌──────┐
       │      │      │      │
    ───┘      └──────┘      └───

弱上拉:  ╱‾‾‾‾‾‾╲      ╱‾‾‾‾‾‾╲
       ╱        ╲    ╱        ╲
    ──╱          ╲──╱          ╲──     ← 上升沿太缓，可能采不到高电平
```

电阻取值参考：

| 总线速率 | 推荐阻值 | 说明 |
|---|---|---|
| 100kHz（标准） | 4.7kΩ | 最常用 |
| 400kHz（快速） | 2.2kΩ | 上升沿要更快 |
| 1MHz+（快速+） | 1kΩ 以下 | 注意低电平灌电流别超 3mA |

**判据**：电阻越小上升沿越快，但器件拉低时的灌电流越大。取 2.2k~4.7k 覆盖绝大多数场景。

### 3.2 常见故障对照

| 现象 | 原因 | 处理 |
|---|---|---|
| 完全无响应 | 上拉没接 / 器件地址错 | 示波器看 SCL 有没有波形，扫描地址 |
| 时通时不通 | 上拉太弱、线太长 | 减小上拉阻值，缩短走线 |
| 第一个字节 ACK 后卡死 | 从机时钟拉伸等待 | 确认主机支持 clock stretching |
| 读数偶尔跳变 | 电源去耦不足 | 器件 VCC 就近加 100nF 电容 |
| SDA 一直被拉低 | 从机死锁（通信中途复位） | 主机发 9 个时钟脉冲解锁总线 |

最后一条值得展开。当 MCU 在通信中途复位，而从机还停在"等待下一个时钟"的状态，会一直拉住 SDA。这时总线彻底瘫痪，重启 MCU 也没用（因为从机还卡着）。**解决办法是手动发 9 个 SCL 脉冲把从机的位移出**：

```c
/* 总线恢复：SDA 被从机拉死时调用 */
static void i2c_bus_recover(void)
{
    /* 先把引脚切成普通 GPIO 开漏 */
    gpio_config_i2c_as_gpio_open_drain();

    /* 发 9 个时钟脉冲，把从机状态机移出 */
    for (int i = 0; i < 9; i++) {
        gpio_clr(SCL_PIN);
        delay_us(5);
        gpio_set(SCL_PIN);
        delay_us(5);
    }

    /* 补一个 STOP 条件：SCL 高时 SDA 由低变高 */
    gpio_clr(SDA_PIN);
    delay_us(5);
    gpio_set(SCL_PIN);
    delay_us(5);
    gpio_set(SDA_PIN);
    delay_us(5);

    i2c_init();     /* 重新初始化硬件 I2C */
}
```

这个函数应该加进所有 I2C 项目的错误恢复路径里。

### 3.3 用软件 I2C 还是硬件 I2C

**硬件 I2C**：省 CPU、速率高，但早期 STM32 的 I2C 外设有已知缺陷（F1 系列的 errata 里明确列了），偶发卡死在忙状态。

**软件 I2C**：用两个 GPIO 模拟时序，速率低（100kHz 左右），但**时序完全可控，不会死锁**，任意引脚都能用。

选型建议：

- 从器件简单、速率要求不高（EEPROM、OLED）→ **软件 I2C 更省心**
- 高速传感器、数据量大 → 硬件 I2C，但**必须加超时和总线恢复**

## 四、SPI：最快，也最容易配错

### 4.1 四个参数决定能不能通

SPI 的配置组合比另外两种多，配错就是读出一堆 0x00 或 0xFF。

| 参数 | 选项 | 说明 |
|---|---|---|
| 时钟极性 CPOL | 0 / 1 | 空闲时 SCK 是高还是低 |
| 时钟相位 CPHA | 0 / 1 | 在第一个还是第二个边沿采样 |
| 位序 | MSB / LSB first | 绝大多数器件是 MSB |
| 数据宽度 | 8 / 16 位 | 屏幕和 Flash 常用 8 位 |
| 片选 CS | 硬件 / 软件 | 软件控制更灵活 |

CPOL 和 CPHA 组合成四个模式：

| 模式 | CPOL | CPHA | 采样边沿 | 常见器件 |
|---|---|---|---|---|
| Mode 0 | 0 | 0 | 上升沿 | **最常见**，Flash、多数传感器 |
| Mode 1 | 0 | 1 | 下降沿 | 部分 ADC |
| Mode 2 | 1 | 0 | 下降沿 | 少见 |
| Mode 3 | 1 | 1 | 上升沿 | 部分屏幕 |

**排查技巧**：先试 Mode 0，不行依次试 1、3。**如果读出来全是 0xFF，通常是 MISO 没接好或器件没供电；全是 0x00，通常是时钟没出来或片选没拉低。**

### 4.2 片选必须手动控制

很多器件的时序要求 CS 在整个传输过程中保持低电平，中间拉高会中止命令：

```c
/* 错误：HAL 每次 Transmit 都会自己控制 CS，多条命令之间 CS 被抬高 */
HAL_SPI_Transmit(&hspi1, cmd, 1, 100);
HAL_SPI_Receive(&hspi1, buf, 4, 100);     /* CS 在两次调用之间被拉高了 */

/* 正确：手动控制 CS，整个交互期间保持低电平 */
HAL_GPIO_WritePin(CS_GPIO_Port, CS_Pin, GPIO_PIN_RESET);
HAL_SPI_Transmit(&hspi1, cmd, 1, 100);
HAL_SPI_Receive(&hspi1, buf, 4, 100);
HAL_GPIO_WritePin(CS_GPIO_Port, CS_Pin, GPIO_PIN_SET);
```

用 CubeMX 时把 `Hardware NSS Signal` 设成 `Disable`，然后自己用一个 GPIO 控制片选——这样最灵活。

### 4.3 高速下的信号完整性

SPI 速率上到 20MHz 以上，就得考虑 PCB 走线了：

- **SCK 走线尽量短**，它是所有信号的参考，最容易产生振铃
- **串一个 22~33Ω 的源端匹配电阻**，抑制过冲
- **MISO 采样相位**可能需要在 Fast Mode 下调整（STM32 的 `SPI_TIMODE`/`SPI_CR2` 里有相关配置）

现象是"低速能通，一提速就出错"，基本就是信号完整性问题。

## 五、用逻辑分析仪排错

这是最实用的部分。三种总线的排错手法是一样的：**先抓波形，再对着手册看时序**。

### 5.1 接线

逻辑分析仪至少要接三根：

- **GND** —— 必须接，否则波形全是噪声
- **SCK/SCL** —— 时钟
- **MOSI/SDA** —— 数据

**触发设置**：让分析仪在时钟信号的下降沿触发，这样能抓到一次完整的传输起始。

### 5.2 解读

以 I2C 读一个传感器为例，抓到的波形应该长这样：

```
START → 从机地址(7位) + R/W → ACK → 寄存器地址 → ACK → 
        RESTART → 从机地址 + R → ACK → 数据高字节 → ACK → 
        数据低字节 → NACK → STOP
```

对照检查：

| 观察到的 | 说明 |
|---|---|
| 有 START 但地址后面是 NACK | 从机地址错，或器件没上电 |
| 有地址 + ACK，但后面没数据 | 寄存器地址错，或器件需要延时 |
| 数据位全是 1 | 从机没驱动 SDA，检查供电和上拉 |
| 时钟频率不是预期的 | 分频系数算错 |

**软件 I2C 抓波形特别有用**，因为你能直接验证 `delay_us` 的时间对不对。

### 5.3 一个真实案例

某次调试 MPU6050，读出的数据一直是 0xFFFF。逻辑分析仪一抓发现：**地址字节后面没有 ACK**。

对着手册一查，MPU6050 的地址是 `0x68`，但 HAL 库要求传**左移一位后**的地址，也就是 `0xD0`（读）或 `0xD1`（写）。传了 `0x68` 自然没人应答。

这个问题不看波形，光看代码是查不出来的——`HAL_I2C_Mem_Read` 返回 `HAL_ERROR`，但不会告诉你为什么。

## 小结

| 接口 | 最容易踩的坑 |
|---|---|
| UART | 用内部 RC 导致波特率偏差；阻塞发送拖慢实时性 |
| I2C | 忘接外部上拉；从机死锁后不会恢复总线 |
| SPI | CPOL/CPHA 配错；片选被自动抬高打断时序 |
| 通用 | 不放逻辑分析仪，靠猜 |

三种总线都掌握之后，你会发现新器件的手册基本能直接读懂，接上去就能通——这时候硬件调试的自信才真正建立起来。
